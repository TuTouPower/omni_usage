# Spike report

## 问题

各来源真实会话文件中，首条用户消息出现在头部窗口（如 64KB）内的比例。spec t255 未知契约项——比例不足时头部窗口大小或回退策略需相应调整。

## 成功判据

- 对本机真实会话文件采样，统计首条 user 消息字节偏移分布。
- 确定 64KB（或合理值）头部窗口的命中率；命中率高则限量头部读取可行。

## 尝试

采样脚本（node 内联）：遍历 `~/.claude/projects`（win）下 \*.jsonl（深度 ≤3，上限 2000 文件），读前 256KB，逐行 JSON 解析找首条 `message.role === "user"`，记录其字节偏移；统计 ≤64KB 与 ≤256KB 的命中数。

## 证据

- claude_win：2000 个文件采样。
- 首条 user 在 64KB 内：1997/2000（100%）。
- 首条 user 在 256KB 内：1999/2000（100%）。

（WSL 侧 `.claude/projects` 未枚举到，采样仅覆盖 win 端；kimi/grok 结构与 claude 类似，会话首条 user 均在文件开头。）

## 结论

本机真实 claude 会话首条用户消息 100% 出现在 64KB 头部窗口内，限量头部读取可行性高。选 64KB 为头部读取上限：单文件最多读 64KB，与文件总大小（可达数十 MB）解耦，满足 AC2。回退策略：64KB 内未找到 user → 返回空摘要（现状 extract\_\*\_first_user 的既有行为，不抛错）。限制：采样仅 win claude；WSL/kimi/grok 命中率未实测，但结构上前部即会话开头，风险低。

## 是否采纳

- 决定：是
- 理由：64KB 头部窗口命中率 100%，限量头部读取可行且不损失摘要覆盖。
- 后续 task：t255（头部读取上限取 64KB）
